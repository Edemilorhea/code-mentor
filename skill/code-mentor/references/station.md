# 寫站：行註解、呼叫鏈與細部說明

流程第 4 步、寫第一站之前讀一次（`概覽` 等級不讀）。站的結構與站層級的欄位在 `plan.md`。

## 欄位

```json
"stations": [{
  "intuition": "（選填）生活類比，再說精確意思與限制",
  "chain": "（選填）呼叫鏈，多行文字，照原樣顯示",
  "notes": [{
    "hunk": "f13#2", "line": 47, "side": "new|old",
    "to": 62, "step": 1, "see": "f14#1:30",
    "kind": "what|how|why|syntax|good|risk|bug|info", "tier": "core|detail", "text": "..."
  }]
}]
```

- 註解 `note`
  - `line` 是該 hunk 內的行號。`side` 預設 `new`；`side: "old"` 用舊檔行號。
  - `to`（選填）：結束行（同一側）。形成**範圍註解**：範圍左側有色條，說明框放在範圍第一行上方，標題 `L47–L62`。
  - `step`（選填）：數字，顯示成編號圓章。用來把一個方法依序一段一段講。
  - `see`（選填）：`"<hunkId|fileId>:<行號>"`，產生可點的交叉參照，跳到「依檔案」分頁該行。
  - `tier`（選填，預設 `core`）：`core` 在四種檢視都顯示；`detail` 只在「前端」「後端」「資料模型」檢視顯示（見下方「core 與 detail」）。
- `check` 會驗證：`to` ≥ `line` 且兩端在 hunk 內；`see`／`mapping` 的目標存在；`tier` 只能是 `core`／`detail`；`chain` 是字串。`導讀`／`教學` 的站跨兩個以上檔案沒有 `chain`、或只有 detail 沒有 core 時會警告。

## 檔案用途（`files[path].purpose`）

- 每寫完一站，替這站引用的每個檔案寫 `files[path].purpose`（已經寫過的檔案不重寫）。這時你剛用 `show` 看過它，不要為此另外讀檔。
- 回答兩件事：**這個檔案是什麼**（哪張資料表、哪個畫面、哪支 API，用專案裡的實際名稱），以及**它在這次修改中為了完成什麼**。一到兩句。
  - 好：「`MainIndustry` 資料表的 Entity：主要行業別總表，530 筆。這次新增，讓帳號申請、事業基本資料、年報共用同一份行業別代碼。」
  - 不好：「新增 Entity。」（沒說是哪張表、為什麼要有）
- 和 `summary` 不同：`summary` 說這次改了什麼，`purpose` 說檔案本身是什麼、為什麼存在。
- 顯示在側窗與「依檔案」分頁的檔案頂部。`導讀`／`教學` 缺少時 `check` 警告（產生檔、略過、刪除的檔案除外）。

## 呼叫鏈（`chain`）

- **呼叫鏈**：`導讀`／`教學` 等級，跨兩個以上檔案的站要寫 `chain`，讓讀者看程式之前先看到整條路。
- `chain`（站，選填）：這站的呼叫鏈，顯示在「我做了」下方。用 `→` 表示呼叫、`├`／`└` 表示分支，右邊對齊寫在哪一層、哪個檔或 API。例：

  ```
  清單頁 useEffect
    → load()                    前端：AuthorizedNaturalPersons.tsx
    → service.getList()         GET /api/AuthorizedNaturalPerson
    → Controller.GetList        後端
    → Query.GetListAsync
         ├ ResolveAccessAsync   目前事業與 canManage（2-e）
         └ 組回應：quota/used/items
  ```

  有寫入資料庫的那一行，行尾加 `⇒ 寫入 <表名>`，例如 `→ Handler.Handle → SaveChanges   ⇒ 寫入 CompanySCUser`。站的程式有新增 `SaveChanges` 而 chain 沒有任何 `⇒` 時，`check` 警告。主線已經講完整條鏈的站，chain 可以縮成一行「本站是主線 p1 第 3 步」。

## 看得懂，不只是「有寫」

每則註解要讓只讀報告、不翻 repo 的讀者回答三個問題：

1. **結果**：這段讓畫面或資料出現什麼結果？
2. **後果**：拿掉或寫錯會怎樣？（core 必答；detail 視情況）
3. **名詞**：裡面有沒有沒解釋的名詞或語法？

- 不要把程式逐字翻成中文。「狀態欄轉成 0／1 字串」是翻譯；「數字小的排前面，所以已授權排在已註銷前面」才是結果。
- 專案名詞第一次出現時先用一句話定義，例如「`useTableSort`：共用的表格排序 hook，頁面告訴它每欄怎麼取值」。同一站只定義一次。
- 引用別站的東西時寫站號，例如「（見 2-e）」。

| | 同一段 `sortAccessors` 的註解 |
|---|---|
| 不及格 | 頁面告訴 hook 每欄怎麼取值。狀態欄轉成 0／1 字串讓已授權在前。 |
| 及格 | `useTableSort` 是共用的排序 hook，它不知道每一欄的值在哪，所以頁面給它這張「欄位 → 取值方式」表。hook 一律用字串比大小，所以狀態先轉成 "0"／"1"：已授權是 0，排在已註銷（1）前面。漏掉某一欄，點那欄的標題就不會排序。 |

`check` 只檢查結構，不判斷看不看得懂。讀者在報告上按「看不懂」會複製一行「看不懂：第 N 站… 檔名 L行號（摘要）」貼回對話，照 `update.md`「使用者說看不懂時」處理。

## core 與 detail

報告有四種檢視：「整體」只顯示 core 註解；「前端」「後端」「資料模型」只顯示那一類檔案，並加上 detail 註解。

| `tier` | 寫什麼 |
|---|---|
| `core`（預設） | 改了什麼、為什麼、核心方法的步驟。只看「整體」也要讀得懂這次修改 |
| `detail` | 預設讀者讀到這裡會卡住、但「整體」可以略過的地方 |

`導讀`／`教學` 等級，下列程式型態**必須**有 detail 註解（已有 core 註解講清楚的除外）：

| 型態 | 要回答 |
|---|---|
| 一組畫面狀態（`useState`、`ref`） | 每個值控制畫面上的什麼；初始值代表什麼 |
| 對照表、排序或比較函式（`statusOrder`、`sortAccessors`、`byStatus`） | 它決定畫面上的什麼結果 |
| 依序取值、預設值（`a \|\| b \|\| c`、`??`） | 取到哪一個、對畫面有什麼影響 |
| DTO／Entity 欄位 | 每個欄位的業務意思；可為 null 代表什麼情況 |
| EF 設定、索引、migration 步驟 | 這條限制擋住什麼資料 |
| 框架慣例（DI、屬性、裝飾器、Hook 規則） | 在這裡起什麼作用 |

- `教學` 的 detail 另外補 `syntax` 註解（`as const`、相減排序、`[..3]`）。`導讀` 的 detail 只講作用，不講語法。
- detail 也要用 `line`～`to` 框住整段：「只看重點」只露出有註解的範圍，沒框到的會被折起來。
- 只有 detail、沒有 core 的站，在「整體」看不到任何說明；`check` 會警告。

## 詳細說明（註解）

導讀的目的：讀者不必自己讀完 diff，就知道**改了什麼、怎麼改、為什麼改、用到的語法怎麼讀**。註解的 `kind` 對應這四件事。`概覽` 等級不寫行註解；`syntax` 只在 `教學` 等級主動寫（`SKILL.md`「深度等級」）。

| `kind` | 回答的問題 | 怎麼寫 |
|---|---|---|
| `what` | 改了什麼 | 行為差異：改之前怎樣，改之後怎樣。修改既有邏輯時，用 `side: "old"` 的註解標舊行為，再用新行的註解標新行為 |
| `how` | 怎麼改 | 這段程式負責什麼、吃什麼輸入、產生什麼結果、交給誰用 |
| `why` | 為什麼這樣改 | 設計原因，以及沒有它時下游哪裡會壞 |
| `syntax` | 語法／用法 | 讀者可能不熟的語法、框架 API 或慣用寫法：它是什麼意思、在這裡起什麼作用 |

- **核心區塊**（含決策、轉換或規則的方法）：至少要有 `what` 和 `why`。方法超過約 15 行時，用 `to` 與 `step` 切成 5–15 行一段，每段一則註解，順序對應程式執行順序。
- **報告預設只顯示「重點」**：有行註解的區塊，只顯示註解的 `line`～`to` 範圍前後 3 行，其餘折成「略過 N 行」；讀者可按「看完整檔案」切到整份。所以核心邏輯一定要用範圍註解（`to`）框起來，沒框到的程式會被折起來。
- **讀者可勾選「隱藏格式化差異」**（只改換行、縮排、空白、單雙引號或結尾逗號的行）。不必為這些行寫註解；註解貼到的行不會被隱藏。
- **次要區塊**（接線、設定、文件）：一則 `what` 就夠，或由該站的「我做了」涵蓋。不必為了數量逐 hunk 填註解。DTO 與畫面狀態不算次要，見「core 與 detail」。
- `syntax` 在該語法**第一次出現**的地方解釋一次。之後再出現時用 `see` 指回去，不要重講。
- 註解貼在**精確的那一行**，不要重述程式碼字面。禁止「某檔承擔本情境、與其他檔共同完成」或剪貼前三行程式碼這類套版文字。
- 意圖是推論時，註解開頭寫「推測：」。無法確認的細節寫「不確定」，不要補造。
- 需要跳到別處時用 `see`。
- `check` 會在「有程式變更但沒有任何註解或 callout」的站警告（`depth` 是 `概覽` 時不警告）。這個警告代表那一站還沒有導讀，不要用一句空話消掉它。

## 直覺層（選填 `intuition`）

- 只在概念抽象時使用。
- 先用一個生活類比，再寫精確意思，最後寫類比的限制。
- 例：「像櫃台領號碼牌（類比）。精確來說，`Outbox` 是…。類比不涵蓋：號碼牌不會重送。」

## 程式導讀結構（參考 code walkthrough）

- 先講這段程式在整體流程中的角色，再逐段走。
- 每段沿同一條線說：為了什麼 → 責任 → 輸入與前置狀態 → 轉換與結果 → 交給誰 → 失敗或拿掉它時下游會怎樣。只列「誰呼叫誰」不算導讀。
- 用 `step` 的編號對應程式裡的順序。被第 3 段呼叫的方法，放在第 3 段之後講，不要另開一條線。
- 正常路徑先講完，再講失敗路徑、替代路徑與邊界情況。
- 看懂下一段程式前必須先懂的機制（例如交易、快取、授權載入），放在用到它的那段程式**之前**，一次只講一個。

## 驗讀

**使用者說「驗讀」或「確保看得懂」時**（預設不做，整份約多 3–5 分鐘）：每站寫完後，派一個 agent 扮演 `plan.md` 的「預設讀者」，只給它這站的文字、註解與對應 diff，不給 repo，請它對每則註解回答「看得懂嗎」的三個問題，列出答不出來的。只補列出來的那幾則，再換下一站。不能派 agent 時，自己照三個問題逐則檢查，並在回覆說「未做獨立驗讀」。
